## Cheat sheet

- **NBIS location:** `~/nbis/bin`, which is **not** on PATH. Override with `export NBIS_BIN=...`.
- **mindtct can't read TIFF.** Images are converted to 8-bit PNG tagged as 500 dpi first.
- **DeepPrint checkpoint:** `DeepPrint_TexMinu`, 256 texture + 256 minutiae dims, 8000 training subjects.
  - Build it with `get_DeepPrint_TexMinu(num_training_subjects=8000, num_dims=256)`.
  - The "512-d" embedding is the two halves **concatenated**. Each half is L2-normalized on its own, so the full vector has norm √2.
- **Dataset:** FVC2004 DB1_B to DB4_B, 320 samples. Each finger in each DB is its own identity: **40 subjects × 8 impressions**.
  - Subject id = `db * 10 + finger` (0–39). File names 101–110 repeat in every DB.
  - Sample order is DB → finger → impression, and every output file uses it.
- **IoM input:** `results/features/deepprint_flx.npz`, field `embedding` (320×512), L2-normalized by `iom.prepare()`.
- **IoM parameters (Paik's preset):** GRP m=300, q=16. URP m=600, w=100, p=2. Score = number of matching hash entries (0–m).
- **IoM keys:** generated from an integer token by a seeded PRNG (`iom.make_key(scheme, token)`), so a key never has to be stored.
- **Week 4 attack targets:** `results/templates/{grp,urp}_stolen_token0.pt` hold the codes; rebuild the key with `make_key(scheme, 0)`.

## Pipeline details

### 1. NBIS
- It was already built in `fixed-length-fingerprint-extractors/nbis_v5_0_0/Rel_5.0.0/` (see `build.log`) and installed to `~/nbis/bin`.
- **Per image:** TIFF → PNG (500 dpi) → `mindtct` → `.xyt`. Large intermediate files are deleted.
- **Matching:** one `bozorth3 -M mates.lis` call scores all pairs. The list file has one pair per two lines.
  - The code raises `maxfiles`, because the default of 10,000 is too small.
  - It checks that the number of scores returned equals the number of pairs.
- **Smoke test:** a genuine pair scored 83, an impostor pair 5.
- On average there are 62 minutiae per image (min 22, max 137).
- DB3 (thermal sensor) is really about 512 dpi, but it is tagged 500. That's fine; mention it in the report.

### 2. DeepPrint preprocessing (same as flx's FVC2004 setup)
1. Read the image as grayscale (OpenCV).
2. Pad it to a square with **white** (`fill=1.0`) and resize to **299×299**.
3. Run flx's Gabor binarizer with a ridge-width setting.

**Ridge-width variants (`--prep`):**
- **`flx` (default):** 1.8 for every DB, exactly as flx does.
- **`scaled`:** `3.8 × 299 / longest side of the image`. This keeps the ridge scale consistent across DB sizes. For DB1 it works out to 1.8.

The two performed about the same (512-d EER 6.25% vs 6.53%), so `flx` stays the default.

**Extraction:** eval mode, no gradients, batch size 32, CPU, about 20 s for all 320 images.

### 3. Pair sets
Only pairs with i < j are scored, so each pair is compared once. (Bozorth3 isn't perfectly symmetric.)

| Pair set | Genuine | Impostor | Notes |
|---|---|---|---|
| `all` | 1,120 | 49,920 | Includes easy cross-DB (cross-sensor) impostors |
| `fvc` | 1,120 | 180 | FVC2004 competition rules: first impressions only, same DB. **FNMR at FMR 0.1% is meaningless here** |
| `db1`–`db4` | 280 each | within-DB | Per-sensor difficulty |

### 4. Metrics
- **Thresholds:** higher score means more similar, and a pair is accepted when score ≥ threshold.
- **EER:** the threshold where |FMR − FNMR| is smallest, reported as the average of the two rates.
- **FNMR at FMR target:** the lowest FNMR whose FMR is at or below the target (1% and 0.1%).
- **d′:** how far apart the genuine and impostor score distributions are. Higher is better.
- **D↔sys (unlinkability, Gomez-Barrero et al. 2018):** compares "same finger, different key" scores with "different finger, different key" scores. 0 = unlinkable, 1 = fully linkable.
  - Estimated with a 30-bin histogram, so it is never exactly 0. `dsys_noise_floor` reports what the estimator gives when there is no linkage at all; compare against that, not against 0.

### 5. IoM hashing (week 3)
- **Code reuse:** `src/iom.py` imports `GRP` and `URP` straight from `Analysis_LSH/LSH.py`, so hashing, `score()` and `lsp()` are exactly Paik's.
- **Keys:** the one addition. Paik's `setup()` draws from torch's global RNG; `make_key()` does the same draw from a `torch.Generator` seeded with the user's token.
  - GRP key: Gaussian matrix (m·q × 512).
  - URP key: m·p random permutations of 512 (`randn(...).argsort()`).
- **Features** are L2-normalized first (Paik does the same). Both IoM variants are scale-invariant, so this changes no hash; it only matters when comparing pre-images to originals later.
- **URP hashing is batched (32 at a time)** because it builds an N × 1200 × 512 tensor (~786 MB for all 320 at once).
- **Token ranges** (kept apart so experiments never share a key by accident):

| Tokens | Used for |
|---|---|
| 0–4 | Stolen-token experiments: one shared key each, for everyone |
| 10,000 + subject | Genuine-token: each finger's own key |
| 20,000 + subject | Revocability: each finger's reissued key |

**Scenarios evaluated:**
1. **Stolen token:** everyone uses the same key, repeated for 5 keys. This is Paik's setting and the attack's threat model (the attacker has code and key).
2. **Genuine token:** every finger has its own key, and impostors use their own.
3. **Revocability:** each finger is re-enrolled with a new key. Old vs new templates of the same finger should look like strangers.
4. **Chance check:** with unrelated keys, the expected score is m/q = 18.75 (GRP) and m/w = 6 (URP).

## Baseline results (pair set `all`, `flx` preprocessing)

| System | EER | FNMR at FMR 1% | FNMR at FMR 0.1% | d′ |
|---|---|---|---|---|
| DeepPrint 512-d (cosine) | **6.25%** | 18.93% | 58.57% | 3.21 |
| DeepPrint texture only (256-d) | 7.95% | 22.50% | 64.20% | 3.14 |
| DeepPrint minutiae only (256-d) | 6.15% | 20.89% | 55.71% | 2.87 |
| NBIS Bozorth3 | **9.03%** | 15.62% | 22.23% | 1.66 |

**EER per DB:**

| | DB1 | DB2 | DB3 | DB4 |
|---|---|---|---|---|
| DeepPrint 512-d | 12.15% | 11.02% | 3.56% | 5.00% |
| NBIS | 11.84% | 14.14% | 5.13% | 5.73% |

**Observations:**
- DeepPrint has the lower EER, but NBIS is much better at strict thresholds (FMR 0.1%).
- DB1 is the hardest subset and DB3 the easiest.
- DeepPrint genuine scores cluster around 0.9 and impostor scores around 0.3.
- These are the numbers that GRP/URP-IoM protected matching gets compared against in week 3.

## Week 3 results: IoM validation (pair set `all`)

**Stolen token (5 shared keys):**

| System | EER (mean ± std) | FNMR at FMR 1% | FNMR at FMR 0.1% | Hashing time |
|---|---|---|---|---|
| Unprotected DeepPrint 512-d | 6.25% | 18.93% | 58.57% | n/a |
| GRP-IoM (m=300, q=16) | **6.58 ± 0.44%** | 21.16% | 60.84% | 0.016 ms/template |
| URP-IoM (m=600, w=100, p=2) | **6.27 ± 0.17%** | 19.00% | 58.98% | 0.62 ms/template |

**Per-DB EER (key 0):**

| | DB1 | DB2 | DB3 | DB4 |
|---|---|---|---|---|
| GRP-IoM | 12.67% | 10.44% | 3.89% | 5.87% |
| URP-IoM | 12.17% | 11.34% | 3.13% | 6.37% |

**Genuine token and revocability:**

| | GRP-IoM | URP-IoM |
|---|---|---|
| Genuine-token EER | 0.00% | 0.00% |
| Chance level (m/q, m/w) | 18.75 | 6.00 |
| Different finger, new key (mean score) | 18.83 | 6.04 |
| Same finger, new key (mean score) | 19.03 | 5.50 |
| Same sample, old vs new key (mean score) | 19.29 | 5.65 |
| Old template accepts new one (at EER threshold) | 0.00% | 0.00% |
| D↔sys (noise floor) | 0.034 (0.031) | 0.054 (0.022) |

**Observations:**
- **Accuracy holds.** Both schemes stay within half a point of the unprotected EER, and their DET curves sit on top of the unprotected one. GRP varies more from key to key (±0.44%) than URP (±0.17%).
- **Genuine-token 0% EER is expected, not impressive.** Impostors with their own key score at chance level, so they are trivially rejected. Stolen-token is the meaningful setting.
- **Revocable and unlinkable.** Same finger + new key scores at chance level, and no reissued template is accepted.
  - URP's D↔sys sits a bit above its noise floor. Five fresh key draws gave a same-finger mean of 5.86–6.38 (both sides of 6) and D↔sys 0.018–0.047, so it's sampling noise from having only 40 independent key pairs.
- **URP hashes ~40× slower than GRP** (0.62 vs 0.016 ms). That's hashing, not the attack, but it's a first data point for extension 1 (why URP takes longer to break).
- **Ready for week 4:** reloading the saved templates and rebuilding keys from tokens, Paik's own `score()` agrees with ours, and Paik's `lsp()` evaluated at the true embedding is ≥ 0 everywhere. That means the true feature satisfies every argmax constraint the attack will search over.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| DeepPrint EER ≈ 50% | Checkpoint didn't load. flx **silently continues with random weights** | Look for `Loaded best model from` in the output; check `models/best_model.pyt` exists |
| Error about tensor sizes when loading the model | Model built with the wrong settings | Must be TexMinu, 8000 subjects, 256 dims |
| `mindtct ... not found` | NBIS isn't installed or isn't found on this machine | `export NBIS_BIN=/path/to/nbis/bin` or rebuild NBIS |
| `image type UNKNOWN : not supported` | A TIFF was passed straight to mindtct | Go through `nbis_match.extract_minutiae()` |
| NBIS results don't change after a preprocessing change | Stale minutiae cache | `rm -r results/features/nbis_xyt/` |
| Assertion error in `run_baseline.py` | Feature file is stale or in the wrong order | Re-run `extract_deepprint.py` |
| `bozorth3 returned N scores for M pairs` | A bad `.xyt` file or the `maxfiles` limit | Inspect the `.xyt` files; check the `maxfiles` argument |
| IoM self-match score below m | Wrong key: token or parameters don't match the saved template | Rebuild with `make_key(make_scheme(name), template["token"])` |
| Out of memory hashing URP | Batch too large (URP builds N × 1200 × 512) | Lower `batch_size` in `hash_all()` |
| `KeyError: 'NBIS-Bozorth3'` in `eda.py` | `run_baseline.py --skip-nbis` overwrote the scores without NBIS | Re-run `python src/run_baseline.py` (no flag) |
| EDA figures pile up at the end, are huge, or leave blank gaps in Overleaf | `figure*` floats to later pages; column-sized figures get blown up in a one-column document; `[H]` leaves gaps | `eda_figures.tex` now detects one- vs two-column and picks the layout and width (`\edafig` macro, `_wide.pdf` variants), with `[!ht]` placement. Upload all 14 PDFs. |
| `ModuleNotFoundError: LSH` | `Analysis_LSH/` moved or renamed | `iom.py` adds `ROOT/Analysis_LSH` to `sys.path`; fix the path there |

- **2026-10-22:** Audited every report number against an independent brute-force recomputation: all match. Fixed misleading presentation: (1) correlation matrix now averages Spearman *within* each DB, because pooling sensors produced a spurious contrast-similarity link (0.45 pooled vs 0.01 within; Simpson's paradox, DB3 is high-contrast and easy to match); the contrast-vs-similarity scatter was dropped for the same reason; (2) class-balance pair counts on a linear scale (log bars from 500 made 1:34 look like 1:3); (3) score histograms labelled as normalized per class; (4) print area and contrast defined in the caption; (5) operating point stated as FMR <= 1% (Bozorth3 reaches 0.69%), EER rows explained. All 7 own-similarity outliers now visually inspected (displaced, dry/light, or wet/blotchy captures).
- **2026-10-22:** Operating point = **FMR 1%** for every system. FMR 0.1% rejects 59% of genuine DeepPrint pairs (656/1,120) and rests on only 49 impostor pairs; FMR 1% rests on 499. Attacks will still also be scored at FMR 0.1% (Paik's setting) as the stricter check.
- **2026-10-22:** Verified DeepPrint extraction is deterministic: a re-run is bit-identical (max diff 0.0).
- **2026-10-21:** Report EDA cut from 10 to 5 figures to fit the 3-4 page limit: image quality + statistics (2x2: NFIQ, print area, contrast, minutiae), own-finger similarity histogram, correlation matrix, genuine/impostor score distributions, class balance. Cut: separate NFIQ plot (merged), feature-value histogram (spread fixed by normalization), contrast scatter (repeats the matrix), DeepPrint-vs-NBIS scatter and t-SNE (extras, still in `results/eda/figures/` for the final report).
- **2026-10-21:** Kept 500 dpi for every DB, including DB3 (truly 512 dpi). The TIFF tags are invalid (1 dpi), so a value must be set. mindtct never rescales by dpi: it uses dpi only for the minutia-quality radius (11 px at 500 dpi, 11.26 → 11 px at 512) and for ANSI/NIST output we don't use. Tested on all 80 DB3 images: 500 vs 512 dpi gives identical `.xyt` and `.min` files.
- **2026-10-19:** Imported Paik's `GRP`/`URP` classes rather than reimplementing IoM, so hashing and `lsp()` match the attack code exactly.
- **2026-10-19:** Used Paik's preset parameters (GRP 300/16, URP 600/100/2) rather than the original IoM paper's, to stay comparable with their attack results.
- **2026-10-19:** L2-normalize the 512-d vector before hashing, as Paik does. No hash changes (IoM is scale-invariant); it keeps pre-image comparisons on the unit sphere.
- **2026-10-19:** Keys come from integer tokens through a seeded PRNG. This matches the IoM design (token → PRNG) and makes every template reproducible without storing keys.
- **2026-10-19:** Attack targets are the stolen-token templates under key 0, because Paik's threat model gives the attacker the code and the key.
